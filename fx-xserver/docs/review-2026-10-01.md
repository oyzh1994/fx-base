# A whole-project review, 2026-10-01

The project is at the end of its build-out: the backlog's own items are down to **A18** (termora's
密钥管理器 button: `Nonexistent button 16`, AWT's own reading of the event) and **A20** (a context menu
that was never reproduced), the suite is 466 tests, and the last two days were spent on what a *user*
sees - smoothness, the pointer, and quitting. This is a review with that lens: read the hot paths,
measure what can be measured, break what can be broken, and write down what is left.

**What this session changed**: two defects, both reproduced first and verified after (A29 and A30 in
`docs/backlog.md`), then two more from the lists below as they became reachable (A31, the VNC tile
work, and A33, the store warning), and a field-by-field answer to the one open correctness item that
had been waiting for an experiment (A18, below).

## Fixed: a window's own pixels had no budget (A29)

Every window keeps its pixels (B5), and its store is **the window's own size** - the one allocation in
this server that had no bound. Measured, on a server started with `-Xmx256m`: a client that creates a
12000x12000 window and draws one rectangle into it (which is what allocates the store) reached

```
ERROR c.ClientConnection - client /127.0.0.1:49611 hit OutOfMemoryError during MapWindow
java.lang.OutOfMemoryError: Java heap space
        at draw.Framebuffer.allocate(Framebuffer.java:86)
        at handler.WindowHandlers.paintBackground(WindowHandlers.java:1267)
        at handler.WindowHandlers.mapWindow(WindowHandlers.java:568)
```

The connection is dropped (that path is deliberate and good), the window never maps, and the *server*
is one allocation away from the same end - 65535x65535 is 17 GB of store. Every other drawable already
had such a budget: a pixmap 16M pixels, an image decode 64M, a BIG-REQUESTS request 16 MB, a WebSocket
message 16 MB, a clipboard 16 MB, and the screen `--max-screen` (8192x8192). The window store was the
gap.

`XWindow.keepsOwnPixels()` now also requires the window to fit that budget
(`MAX_STORE_PIXELS = 8192 * 8192`, the largest screen this server can be asked for). Nothing about the
window is refused: it draws straight onto the screen, which is the path the root already takes, and
every caller of `keepsOwnPixels()` already had a branch for it. **No window that fits on the display is
affected.** After the fix the same 12000x12000 client maps and draws (`CreateWindow, MapWindow,
CreateGC, PolyFillRectangle` all executed, no OOM, clean disconnect), and `WindowTreeTest` pins the
rule without allocating anything.

## Fixed: the ZRLE encoder's palette search ran past the point of being useful (A30)

The frame-path work (A24) and the wire work (A25) made a viewer of an unchanging screen free, so what
is left of the VNC path's cost is encoding what *does* change. Measured with a harness in the
encoder's own package (`ZrleCost3`, min of 36 runs per content type, full 1300x800 frame):

| content | before | after |
|---|---|---|
| two colours (a plain terminal) | 9.8-10.1 ms | **9.8-10.1 ms** |
| text-like (runs and six greys) | 13.5 ms | **13.6 ms** |
| photo-like (every pixel different) | 79-100 ms | **57 ms** |

The encoder was looking every pixel up in a palette of up to 128 colours - but **past sixteen colours
the tile can only be plain RLE or raw, and neither reads the palette**, so the search from the
seventeenth colour on was pure work, and a photo-like tile spends most of its pixels there. The search
now stops at `PALETTE_LIMIT` (and the per-tile palette array is 17 ints instead of 128, which is a
little less garbage per tile too). Two-colour and text-like tiles are unchanged, which is what the
table is for: the common case must not pay for the rare one.

## Fixed: one rectangle per update became the tiles that changed (A31)

A25 made an update the **box** the differing pixels are in, which is right for one change and wrong for
two: a status line and a spinner in opposite corners were one rectangle spanning the screen, and a
full-screen ZRLE frame is 10 ms of one core in flat colours and 57 ms photographic (the table above).
`RfbSession` now builds the update the way `x11vnc` does: the region in 64x64 tiles, a changed tile
merged with the changed tiles beside it into a run, and **each run shrunk to the box of the pixels
that really differ** - so a small change is still the few pixels it is, and scattered changes are
several small rectangles instead of one big one. A region that changed everywhere is still sent as one
rectangle, because one rectangle compresses better than a band's worth of them.

The test for it drives **one** `PolyFillRectangle` with two rectangles in it (one request, so the tick
cannot split it and the damage really is one rectangle), and it was checked against the old behaviour:
the old code sends `[5, 5, 285, 185]` - the whole window - where the new one sends two 10x10
rectangles. `RawXClient.fillRectangles` is the harness piece that made that possible.

## Fixed: the store budget has a breadcrumb (A33)

A29's budget depends on every caller asking `keepsOwnPixels()` first. They all do (audited), and
`ownPixels()` now writes **one warning per window** when it is asked for the pixels of a window that
keeps none - so a future caller that gets this wrong produces a log line naming the window and the
budget instead of an `OutOfMemoryError` with no explanation.

## Answered: A18's button, field by field

The one open correctness item had been waiting for "the two servers' bytes have not been diffed field
by field yet". They have been now: a raw client that selects `ButtonPress|ButtonRelease|MotionNotify`
on its own window and prints every field, run against this server and against `Xvfb :98` on `.147`
with the same click driven by `tools/kit.sh Drive`. **Every semantic field is identical** - type and
detail, root/event/child, all four coordinates, `state` (0x0 on the press, 0x100 on the release) and
`same_screen` - and the only differences are the ids a server picks for itself and the documented
clock base (this server's wall-clock milliseconds against Xvfb's uptime). The `button 16` AWT reports
is therefore **not in our bytes**; its own dump (a 32-bit garbage `x`, the *previous* event's
coordinates in `state` and `button`) is a struct read out of a stale buffer, which is a client-side
desynchronisation. The next experiment is written into the A18 entry: a **raw-byte** probe (not one
that parses the length fields the client parses, which cannot see a desync) in front of this server
while termora is the client, checking the `length` field of every **XI2 GenericEvent** against the
bytes actually sent - termora selects XI2, and a generic event whose length and payload disagree is
exactly how a stream loses its footing while a chunk-logging tap still looks well-framed.

## Measured, and left: what a full-screen change costs

The same harness, extended numbers, is the clearest performance statement about the VNC path:
**a full-screen ZRLE update is 10 ms (flat colours) to 57 ms (photographic) of one core.** At 60
frames a second that is 60% to 340% of a core, before the socket. What makes this survivable today is
A25: an update is the **box the differing pixels are in**, and an unchanged screen is not sent at all,
so a terminal that repaints identical content costs nothing and a small change costs a small box. What
is *not* covered, and is the biggest remaining performance item:

- **one rectangle per update.** A change that lands in two corners is encoded as one bounding box that
  spans both. Encoding the changed **tiles** (what `x11vnc` does) would cut both the bytes and the
  encode time, and the decoder side is the same ZRLE. M.
- ~~**no Tight (or JPEG) for photographic content**, where ZRLE-raw is 3.1 MB and 57 ms for one
  frame.~~ **Done the same day (A32)**: a rectangle whose sampled colours say "photograph" goes as
  Tight's JPEG method when the client offers it, and the wire measurement is 3.12 MB -> 0.70 MB for the
  same full-screen change (encoder: 56 ms -> 31 ms). Text and flat panels stay on ZRLE, which is
  lossless - the rule's other half, and the reason it is a rule rather than a flag.
- **the encode happens on the session's own thread.** That is what keeps a slow client from touching
  anybody else (the RFB backpressure story), and it also means one slow encode delays that client's
  next update. Encoding a different rectangle while the previous one is on the wire would need care
  with the session's single `Deflater`. M.

Server CPU in the bed (server on `.147` with `--backend vnc`, EasyShell's aliyun tab open): this run
read **1.4% of a core with nothing happening** because the app was showing its own "connection timed
out" dialog and not painting; with the terminal actually open it is the ~20% of A24, which is the
application redrawing itself ~300 times a second. The server's own share of that is the frame path
before A24 and the tick's compare after A25 - both measured, both small now.

## Checked, and found sound

Worth recording, because the review's job is also to say what does not need work:

- **Every client-controlled allocation has a budget** - pixmaps, image decodes, BIG-REQUESTS, WebSocket
  messages, clipboard text, the screen. The window store was the single gap, and it is closed.
- **Threads**: every listener, poller and writer is a daemon or is closed by `stop()`; the display loop
  is deliberately not a daemon and `Main` joins it (A27). No per-window or per-client thread is left
  behind: a window's debug pulse probe is a JavaFX `AnimationTimer` on the toolkit's thread, not a
  thread of its own.
- **Shared state**: `clients` and `sessions` are copy-on-write, `screenInputs` is a
  `ConcurrentHashMap`, and the rest is under the server lock by convention - the clipboard bridge takes
  that lock itself before touching the selection table, which is the one place a non-request thread
  does (`ClipboardBridge.poll`).
- **An unimplemented request throws** `BadImplementation` rather than silently doing nothing, so a
  client that asks for something this server does not have is told.
- **Resource freeing** happens per window, per pixmap and per connection, and a disconnected client's
  screens are freed with it ("screen of display :N freed").

## Found, and left for later

Each of these is real but not urgent, and none of them is a behaviour a user reported. Sizes are
rough: S is an afternoon with a test, M is a day, L is a feature.

1. **`XWindow.ownPixels()` can still be called for a window that keeps no pixels.** The new budget
   relies on callers asking `keepsOwnPixels()` first; all eight call sites do today (audited), and a
   future one that does not would quietly reintroduce the allocation. A debug assertion or a warning
   inside `ownPixels()` would make the invariant enforceable. S.
2. **DBE on a window with no store** (the root, or one too large to keep pixels):
   `DbeExtension.swap` calls `ownPixels()` directly, which would allocate a store for it. Unreachable
   today - DBE buffers are pixmaps and are capped at 16M pixels, so a window too large to keep pixels
   cannot have live buffers, and the swap returns early - but it is the one place a future change
   could make reachable. S.
3. **`RfbSession.sentPixels` is a full screen of ints per viewer** (4 MB at 1300x800, one per session):
   what makes A25 possible, and proportional to the framebuffer rather than to the change. A tile
   checksum or a two-buffer scheme would be smaller; the comparison (a row-wise `Arrays.equals` over
   the damage) is already cheap. S-M.
4. **The atom table grows with every distinct interned name and never shrinks**, exactly as a reference
   server's does. A client that interns names in a loop can grow it without bound. Recorded rather than
   changed: matching the reference is the point, and a cap would break clients that legitimately
   intern many names. S.
5. **A stop that asked a client to close waits up to `--close-grace-ms`** (2 s by default) for it to
   go, and only when something was actually asked (A27). That is the price of letting an application
   quit cleanly on the way out; `--close-grace-ms` is the knob, and a shorter wait for the stop path
   alone would be easy if the delay is ever noticed. S.
6. **`applicationActive()` is a static count of focused windows.** A window that dies with the toolkit
   (not through the close request the backend sees) would leave the count high, which would draw
   sprites while the process is in the background. Only reachable while the toolkit is going away,
   which stops the server. S.
7. **Test gaps - one closed as unreachable, one explained.** The "resize the screen, then diff" test
   the first version of this list asked for cannot be written for the VNC path: the screen grows only
   from `applyRequestedSize`, which is a **host window drag**, and a VNC backend has no host window, so
   `RfbSession.screenResized()` never fires there (it is kept as a defensive reset of `sentPixels` for
   a future backend that has both). The host-cursor policy has a unit test and cannot have an
   integration one: the platform's own record of whether the pointer is hidden is exactly the cache
   that was stale in A28, so only a screenshot can see it, and that needs Screen Recording permission
   and a real session - which is why the harness (`CGCursorIsVisible`, a region `screencapture`, a
   pixel count against the background) lives in the session's memory instead. S.
8. **A20 stays open** as the backlog has it (never reproduced on either server), and **A18 is
   narrowed** rather than closed: our bytes are now proven identical to the reference's field by
   field, so what is left is a client-side desync and the XI2-length experiment above.

## Design observations, no change proposed

- **Keeping every window's pixels** is what makes a reveal ask nobody to draw and lets a covered window
  go on drawing (B5). The price is memory proportional to the sum of window areas, now bounded per
  window; a window too large to keep them degrades to the root's own path. That is the right trade for
  a forwarding server, where the windows are the applications the user is looking at.
- **One thread writes to a backend** (the display tick): every ordering question - damage, the viewport,
  the sprite, the window's size - has one answer, and nothing has to be locked inside a toolkit. The
  price is up to one tick (16 ms) of latency between a client drawing and a frame going out, which is
  below what a person notices and in the same range as the VNC client's own refresh.
- **A screen per client** costs memory proportional to clients × screen. That is what one window per
  application buys (C8's design), and E4's lazy allocation is what keeps an idle client cheap.
